# Review: Breach Kit (per-customer secret clean-up that a platform hands its users after a breach)

*Project Bot review · 22 Oct 2026, 10:35am AWST (Perth time) · thesis: /workspace/idea-bot/theses/2026-10-22-1015-breach-kit.md (idea bot, 10:15am AWST) · room notes: none saved for this thesis*

## Verdict
- **Score: 5.5/10.** The pain is real, recent and expensive, and it's a smart move to aim at the platform rather than the customer. But nobody has shown a platform will pay for this before it gets breached.
- **Does the gap hold up? Partly.** Nobody sells this as a product to platforms, which is true as far as I could find. But platforms have already built the core of it themselves, in days, mid-incident. After its January 2023 breach, CircleCI shipped an open-source [Env-Inspector](https://github.com/CircleCI-Public/CircleCI-Env-Inspector) that lists every stored secret by name without values. It also added `updated_at` timestamps so customers could prove they'd rotated, revoked old tokens on customers' behalf, and had GitHub rotate all OAuth tokens. And the "kill the key at the issuer" step is already partly automatic: OpenAI, Anthropic and AWS are GitHub secret scanning partners that revoke reported keys, and Railway says it asked the upstream providers to "revoke all keys proactively".
- **Biggest correction or risk:** the thesis treats in-house builds as a risk to test. In fact it has already happened (CircleCI 2023, and Railway this week rotating every bucket credential for its customers). What's left is the per-customer page with live/dead status per secret and a claim pack, sold to a buyer who only feels the need once a breach hits. The thesis also missed a third case that strengthens its "pattern" argument: Braintrust (an AI eval and proxy platform) had every customer's AI provider keys exposed in May 2026.

## 1. Fact-check

**Verified**
- **Railway's disclosure** says what the thesis quotes: an unauthorised party "may have accessed encrypted environment variables and, for some of them, obtained the decrypted contents"; "part of a series of attacks recently targeting platform companies with the aim of compromising AI inference providers"; upstream providers notified "to revoke all keys proactively"; "All deployments are paused"; affected customers to be emailed as confirmed ([Railway disclosure](https://blog.railway.com/p/security-disclosure-wednesday-october-21st)). **Timing detail:** the post went up at 20:44 UTC on 21 Oct, which is 4:44am AWST on 22 Oct. The incident started at 07:24 UTC on 21 Oct (3:24pm AWST) ([OneSignalDesk timeline](https://onesignaldesk.com/news/railway-security-disclosure-environment-variables-rotate-keys), [Railway status](http://status.railway.com/incident/QH8L8B3E)). Still no per-customer exposure list as of this run.
- **The HN thread** is real: "Security Disclosure", 328 points and 171 comments at 10:35am AWST ([HN item 50188228](https://news.ycombinator.com/item?id=50188228)).
- **OpenCode (BleepingComputer, 19 Oct):** 1.4% of OpenCode Console users affected; "more than $1,700 in unauthorized charges overnight" (user reports, ranging from several hundred USD up to $1,700); some Google Cloud projects suspended; earliest possible exposure 17 Oct 00:30 UTC (8:30am AWST 17 Oct); the email "mentions the possibility of reimbursement" ([BleepingComputer](https://www.bleepingcomputer.com/news/security/opencode-hack-exposes-api-keys-amid-ai-distillation-attacks/)). Note that OpenCode *did* email only the affected subset, so its customers knew they were hit, though not which key had been used.
- **Brello** matches the description: usage-only monitoring per key for OpenAI and Anthropic, plus "Already hit? Get help with your case", which organises evidence and drafts the first message to the provider. That help is free during early access, and the pricing shown is "planned" ([Brello](https://brello.app/)).
- **Kingfisher** is Apache-2.0 with 1,270 stars, last pushed 20 Oct 2026 ([GitHub](https://github.com/mongodb/kingfisher)).
- **GitHub's revocation API** is unauthenticated, accepts up to 1,000 tokens per request, and is limited to 60 requests an hour. It only covers GitHub token types (`ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghr_`), and owners are notified ([GitHub docs](https://docs.github.com/en/rest/credentials/revoke)). That's 60,000 GitHub tokens an hour at most, which is plenty for a platform.

**Wrong, unsupported or out of date**
- **"Each platform sent one generic 'rotate everything' message."** Half true. Railway did, but OpenCode emailed only the affected 1.4% and gave an earliest-exposure time. That's still short of a per-secret list, but it's more than generic.
- **Missing prior art (the big one): CircleCI, January 2023.** In response to its breach, CircleCI built and released a secret-finding script, then the open-source [CircleCI-Env-Inspector](https://github.com/CircleCI-Public/CircleCI-Env-Inspector), which lists every project and context secret by name and creation time and never returns values. It also added `updated_at` to its Contexts API so customers could confirm rotation, revoked all project and personal API tokens created before 5 Jan, and had GitHub rotate all OAuth tokens for its customers ([CircleCI incident report](https://circleci.com/blog/jan-4-2023-incident-report/), [CircleCI security alert](https://circleci.com/blog/january-4-2023-security-alert/), [CircleCI secrets tooling post](https://circleci.com/blog/new-features-secure-secrets-management/)). That's steps 1, 3 (partly) and 5 of the proposed MVP, built in-house within days by the breached platform. It's the clearest evidence for the "platforms build it themselves" risk.
- **Missing case: Braintrust, May 2026.** An AWS account holding customer integration data was breached on 4 May, and every customer was told to rotate every provider key the platform held. SecurityWeek reportedly found more customers seeing provider-usage spikes inside the disclosure window ([Harper Foley analysis](https://www.harperfoley.com/blog/braintrust-breach-eval-credential-warehouse-soc2-gap), a secondary source; I didn't open the SecurityWeek piece). This *supports* the thesis: it's a third platform holding AI keys in six months, and it adds AI eval and observability platforms as a target segment.
- **"Bulk revocation where issuers offer it (GitHub's revoke API)."** Understated. OpenAI (since 2021) and Anthropic (since August 2024) are GitHub secret scanning partners that automatically revoke reported keys and notify owners, and AWS is a partner too ([GitHub changelog: OpenAI](https://github.blog/changelog/2021-06-08-rubygems-adobe-and-openai-are-now-github-secret-scanning-integrators/), [GitHub changelog: Anthropic](https://github.blog/changelog/2024-08-20-anthropic-is-now-a-github-secret-scanning-partner/), [supported patterns](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns)). So the AI issuers this campaign targets already run revocation pipelines, and Railway used its own provider contacts on day one. That shrinks the "liveness checker" value: if the issuer revokes everything, the key is dead without the kit. It still matters for issuers without such a pipeline (Stripe, databases, smaller AI providers, OpenRouter-type gateways), and for showing customers proof.
- **The Gemini bill story is a weak signal.** The [Ask HN post](https://news.ycombinator.com/item?id=50168795) has 10 points and 3 comments. It's real, but it shouldn't sit next to the Railway thread as equal evidence. It's also a leaked key, not a platform breach, which is Brello's territory.
- **"Railway had to write per-provider clean-up guides by hand."** Supported by the linked guides. Also worth adding: Railway rotated every storage bucket credential for its customers itself ([status page](http://status.railway.com/incident/QH8L8B3E)), which again shows platforms will do the bulk work in-house.
- **"4 to 6 weeks, one or two engineers"** for an MVP that runs inside a platform's network and handles decrypted secrets is optimistic for anything a security team would deploy. The OSS CLI in 2 to 3 weeks is realistic. Getting through a platform's security review is the slow part, and that's an estimate.

## 2. Competitor check

| [CircleCI-Env-Inspector](https://github.com/CircleCI-Public/CircleCI-Env-Inspector) | Breached platform's own OSS tool listing every stored customer secret by name, no values | High on the inventory step; proves platforms build it in-house | Free (CircleCI-only) |
| GitHub secret scanning partner program ([docs](https://docs.github.com/en/code-security/tutorials/secret-scanning-partner-program)) | Issuers (OpenAI, Anthropic, AWS and many more) take reported keys and revoke them | High on "kill the key at the issuer" for the big AI providers | Free |
| [Brello](https://brello.app/) | Customer-side per-key usage monitoring for OpenAI and Anthropic, plus a help-with-your-claim service | High on the claim pack | Free scan; Pro planned, price not final |
| [Kingfisher](https://github.com/mongodb/kingfisher) | Detection, live validation, blast radius, one-command revoke | High as the engine; the thesis plans to build on it | Free, Apache-2.0 |
| [TruffleHog Analyze](https://trufflesecurity.com/blog/trufflehog-now-analyzes-permissions-of-api-keys-and-passwords) | Key owner, resources and permissions | Medium (engine) | Free OSS / paid enterprise |
| [Doppler breach remediation](https://www.doppler.com/solutions/use-cases/breach-remediation) | Who read which secret, instant rotation | Medium, only if secrets live in Doppler | Paid tiers (not rechecked) |
| [Profero Rapid-IR](https://profero.io/rapid-ir/) | Incident-response team for the breached company | Low to medium; a likely partner or channel | Quote-based |

I found no product sold to platforms for this exact job. A search for platform-side, per-customer secret breach tools turned up dark-web credential monitoring for MSPs (Breachsense, Tenvara), which is a different problem.

**Does the gap hold?** Narrowly, and only in this shape: a ready-made, tested kit that a mid-sized platform (no IR team) can switch on within hours, giving each customer a page that lists their secrets, shows whether each is still live, and helps them claim money back. The pieces exist as free OSS, issuer programs and in-house precedent. The value is speed and polish on breach day, and that's a services-shaped business.

## 4. Build plan (2 to 4 weeks)

**Re-scope first.** Don't lead with an annual readiness subscription. Lead with a **free open-source breach-day kit plus a paid emergency activation**, and let insurers or incident-response firms be the channel. They feel the cost on every incident, and platforms don't until it's their turn.

**Suggested stack:** Go or Rust CLI (one static binary, easy for a security team to audit), wrapping Kingfisher's detectors and validators where the licence allows (Apache-2.0); SQLite output holding only fingerprints and status; a small self-hosted web app (Go plus HTMX, or Next.js) for customer pages, with signed links, deployed inside the platform's own infrastructure; issuer playbooks as plain YAML in the repo so anyone can add issuers.

**Features in order**
1. **Week 1:** a classifier CLI. It takes an env export or JSON dump and gives, per secret: customer ID, variable name, issuer and type, fingerprint (hash plus last 4), and created and updated times. It never prints or stores values, and it's tested on synthetic exports only.
2. **Week 1:** a liveness checker. It re-runs no-side-effect validation for the top 10 issuers (OpenAI, Anthropic, Google AI, AWS, GitHub, Stripe, OpenRouter, Postgres URLs, Slack, Twilio) on a schedule and records live or dead with a timestamp.
3. **Week 2:** issuer playbooks (YAML). For each issuer: revoke link, how to check for misuse by key, whether it's a GitHub scanning partner (bulk report route), and the downtime trade-off when the host can't deploy.
4. **Week 2:** a per-customer page with a signed link. It shows that customer's secrets, live or dead status, playbook steps and a "mark rotated" button, so the platform can see progress.
5. **Week 3:** a platform dashboard showing exposed live secrets remaining by issuer over time, plus bulk export by issuer (GitHub revoke API batches, CSVs for issuers' abuse contacts).
6. **Week 4:** a claim pack. The customer uploads a usage CSV (OpenAI or Anthropic usage by key ID), and the kit marks usage after the exposure start against a 14-day baseline. Talk to Brello about partnering before building this.

**First 10 users**
- Publish a factual breach-day timeline of CircleCI 2023, Braintrust (May 2026), OpenCode and Railway from public sources only, showing what each customer had to work out alone. Post it where those threads already are (HN, X), from Ethan's accounts only with his approval.
- Release the OSS CLI with a "run it on your own env export" demo. Developers whose keys sat on Railway are users even if platforms aren't yet.
- Ask 5 smaller platforms that store customer AI keys (agent platforms, LLM gateways, eval tools) to run the free readiness scan. Outreach only with Ethan's approval.
- Approach 2 incident-response firms or cyber insurers as referral partners, since they're on every breach call.

**The one experiment that kills or confirms it fastest (week 1, before building the dashboard):** ask 10 security or infrastructure leads at platforms that store customer keys (ideally including OpenCode, Railway and Braintrust) two questions. First, would they install the free kit now, before any breach? Second, would they pay a fixed fee to have it running within 4 hours of a breach? Outreach needs Ethan's approval. **Kill** if fewer than 3 would install it and none would talk about paying. That would mean platforms will keep doing it by hand, as CircleCI and Railway did. **Confirm** if 2 or more ask for a pilot, or if one insurer or IR firm wants to bundle it. (These thresholds are our own estimates, not industry figures.)
